核心理念
💡 把 Claude Code 当成高级实习生，而非魔法 理念

Claude Code 能完成大量重复性、结构化的工作，但需要你提供清晰的上下文、明确的目标和适时的纠错。给它写清楚需求文档，而不是"帮我做个电商网站"。

  • 提供足够背景：项目技术栈、代码规范、业务逻辑
  • 分解任务：复杂功能拆成小步骤，逐步验证
  • 保持对话连续性：不要频繁新建对话，保留上下文
  • 不要一次性提过长需求，容易跑偏
🗂️ CLAUDE.md 是你最重要的配置文件 必做

在项目根目录创建 CLAUDE.md 文件，Claude Code 每次启动都会读取它。把项目规范、架构说明、禁止操作写在里面。

CLAUDE.md # 项目规范
- 使用 TypeScript，禁止 any
- 组件使用 Tailwind CSS，禁用 inline style
- 提交前必须运行 pnpm test
- API 路由统一放 /src/api 目录
# 禁止操作
- 不得修改 migrations/ 目录
- 不得删除环境变量文件
💡 快速上手建议： 新人先看「新项目搭建模板」快速落地；接手历史项目看「历史项目改造模板」；遇到 Bug 直接翻「Bug 调试专项模板」；日常开发常备「提示词模板速查库」。

Git PR 自动化管理

让 Claude Code 自动创建分支、提交代码、生成 PR 描述，并处理 review 意见，大幅降低多人协同的沟通成本。

标准工作流
🌿 让 AI 自动创建规范分支并提交 推荐流程

在 CLAUDE.md 中定义分支命名规范，然后每次给 Claude Code 任务时，附上"完成后创建 PR"的指令。

Prompt 示例 # 给 Claude Code 的完整任务指令
实现用户登录功能（JWT 认证）。

完成后请：
1. 创建分支 feat/user-login
2. 原子化提交（feat/fix/chore 前缀）
3. 用 gh pr create 创建 PR
4. PR 描述包含：改动摘要、测试方法、截图
  • 分支命名统一：feat/ fix/ chore/ 前缀，避免混乱
  • 使用 GitHub CLI (gh) 工具，Claude Code 可直接调用
  • PR 模板放在 .github/pull_request_template.md
📝 自动生成高质量 PR 描述 提效

让 Claude Code 在创建 PR 时，自动 diff 分析变更并生成结构化描述，让 reviewer 一眼看懂改了什么。

Prompt 分析 git diff main 的所有变更，
用以下格式生成 PR 描述：

## 改动摘要
## 核心变更文件
## 如何测试
## Breaking Changes（如有）
🔍 自动处理 Code Review 意见 注意

将 reviewer 的评论粘贴给 Claude Code，让它逐条修复并回复评论，但要注意让 AI 解释修改原因，不要盲目应用。

Prompt 以下是 PR review 意见，请逐条处理：
[粘贴 review 评论]

要求：
- 每条意见单独一次 commit
- 说明为什么这样修改
- 不确定的意见请标出，不要擅自改
⚠️ AI 有时会"过度修复"——它可能改了 reviewer 没有提到的地方。每次 review 处理后务必执行 git diff 检查。
🤝 多人协同 PR 合并策略 团队
  • 设置 Branch Protection：main 分支要求 PR + CI 通过
  • 每个 AI 任务独立分支，避免多 agent 写同一文件
  • 用 GitHub Projects 看板管理 AI 正在处理的任务
  • 建议每天 rebase 同步 main，减少合并冲突
  • 可以让 Claude Code 在 PR 合并前自动运行 lint + test

多 Agent 并行协作

同时开启多个 Claude Code 实例处理不同任务，实现真正的并行开发——需要合理划分任务边界。

并行策略
✂️ 任务划分原则：文件级隔离 核心原则

多个 Agent 并行时，最重要的原则是每个 Agent 操作不同的文件/目录，否则会产生 git 冲突甚至相互覆盖。

✅ 好的任务拆分
Agent A → 前端页面 /src/pages
Agent B → API 接口 /src/api
Agent C → 数据库 /src/db
Agent D → 写测试 /tests
❌ 危险的任务拆分
Agent A → 修改 utils.ts
Agent B → 也修改 utils.ts
Agent C → 修改 main.ts
Agent D → 也修改 main.ts
🎭 角色分工模式 推荐

给每个 Agent 设定明确角色，通过不同的 CLAUDE.md 或 系统 Prompt 约束其行为范围。

  • 前端 Agent：只操作 /src/components、/src/pages
  • 后端 Agent：只操作 /src/api、/src/services
  • 测试 Agent：只写/改 /tests 目录，不动源码
  • 文档 Agent：只更新 docs/ 和注释
  • DevOps Agent：只碰 CI/CD、Dockerfile 等配置
📡 Agent 间通信：通过文件传递状态 技巧

多个 Agent 之间没有直接通信能力，但可以通过共享文件（如 TODO.md、接口定义文件）来协调。

协作流程 # 1. 先让架构 Agent 生成接口定义
api-contract.ts → 所有 API 类型定义

# 2. 前端 Agent 依照接口 mock 数据开发
# 3. 后端 Agent 实现接口
# 4. 最后整合测试

# 关键：接口文件由专人（人工）维护

冲突处理与代码合并

多人 + 多 AI 协作时，代码冲突是家常便饭。让 Claude Code 帮你分析和解决冲突，但要注意人工最终校验。

🩺 让 AI 分析冲突并给出解决方案 实用

遇到 merge conflict 时，将冲突内容贴给 Claude Code，让它分析两端的意图并给出合并建议。

Prompt 以下是 merge conflict 内容：
[粘贴 <<<< ==== >>>> 冲突块]

请分析：
1. HEAD 端改了什么，意图是什么
2. incoming 端改了什么，意图是什么
3. 如果两个都要保留，给出合并后的代码
4. 如果有业务逻辑冲突，标出需要人工决策的地方
⚠️ 业务逻辑冲突（如两种不同的折扣计算方式）必须由人来决策，不要让 AI 自己选择。
🛡️ 预防冲突的最佳实践 预防
  • 每天开始工作前先 git pull --rebase，同步最新代码
  • 每个 PR 保持小而聚焦，不要大而全的功能 PR
  • 提前约定共享文件的修改规则（如 config、types）
  • 接口定义文件用版本号管理，避免直接修改
  • 长时间未合并的分支是最大冲突源，尽量缩短 PR 生命周期

核心 Prompt 技巧

同样的任务，不同的 prompt 写法可能导致截然不同的结果。掌握这些基础技巧，再结合下方专项模板，让 Claude Code 理解你真正想要什么。

📋 结构化任务 Prompt 模板 必学
万能模板 【背景】 我们是 B2B SaaS，使用 Next.js 14 + Prisma

【任务】 实现订单列表页面，支持分页和状态筛选

【约束】
- 使用已有的 OrderCard 组件
- API 路由遵循现有 /api/v1/ 规范
- 不要修改 Prisma schema

【完成标准】
- 分页正常工作
- 筛选条件可以组合
- 有 loading 和 empty state
🔁 迭代优化而非一次到位 策略

不要期望一个 prompt 产出完美代码，采用"实现→检视→优化"的迭代模式更高效。

  • 第一轮：让 AI 给出方案骨架，先不写实现
  • 确认方案后，再让 AI 实现核心逻辑
  • 运行测试/看效果，把问题描述给 AI 修复
  • 最后让 AI 做代码审查和优化建议
🎯 用示例代替描述 黄金技巧

与其花大量文字描述代码风格，不如直接给出 1-2 个已有文件作为示例，让 AI 学习并保持一致。

Prompt 参考 src/components/UserCard.tsx 的代码风格，
实现一个类似的 ProductCard.tsx 组件。
需要展示：产品图、名称、价格、库存状态。
✅ 这比写"使用函数式组件，用 tailwind，要有 TypeScript 类型…"效果好 10 倍。
🚫 明确说"不要做什么" 避坑
  • 不要安装新的 npm 包（除非我明确同意）
  • 不要修改测试文件，只修改源码
  • 不要重构现有功能，只实现新功能
  • 不要修改数据库结构
  • 不要删除任何已有代码（可以注释掉）

把这些"禁令"写进 CLAUDE.md，一劳永逸。

历史项目改造模板

接手老项目、在已有代码库上新增功能、重构遗留代码——这些场景需要 AI 先"读懂"项目再动手，否则很容易破坏现有逻辑。

改造/重构 历史项目
第一步：项目摸底
🔍 模板 1 · 接手项目快速摸底 第一步必做

接手任何历史项目，第一件事是让 AI 帮你梳理全貌，而不是盲目开始改代码。

复制即用 · 项目摸底模板 请帮我分析这个项目，我刚接手，需要快速了解全貌。

请依次完成：
1. 读取 package.json（或 requirements.txt / go.mod），
   列出核心依赖和版本，标出过时的包
2. 分析目录结构，画出模块关系图（文字版）
3. 找出项目入口文件，描述主要数据流
4. 列出所有 TODO/FIXME/HACK 注释，按数量排序
5. 统计哪些文件代码量最大（可能是核心或问题文件）
6. 检查是否有未使用的依赖或死代码

输出格式：
- 用 Markdown 表格整理依赖状态
- 给出"需要立即关注"的 Top 3 风险点
🗺️ 模板 2 · 理解特定模块逻辑 读懂再改

在修改某个模块之前，先让 AI 解释清楚它的工作原理，确认理解正确后再动手。

复制即用 · 模块理解模板 我需要修改 [文件路径或模块名]，
但先不要做任何改动，请帮我理解它：

1. 这个模块的职责是什么？解决什么问题？
2. 它被哪些地方调用？（找出所有 import/require）
3. 它依赖了哪些外部状态或副作用？
4. 有哪些边界情况或特殊处理需要注意？
5. 如果我要改 [具体功能]，
   哪些地方会受到影响？

# 理解确认后，再发下一条消息让它改
第二步：安全改造
➕ 模板 3 · 在历史项目中新增功能 最常用
复制即用 · 新增功能模板 【项目背景】
这是一个 [技术栈] 项目，已运行 [X] 年，
代码风格参考 [示例文件路径]

【新增功能】
需要新增：[功能描述]

【硬性约束】
❌ 不得修改以下文件（生产稳定）：
   [列出不能动的文件]
❌ 不得修改数据库结构
❌ 不得升级任何依赖版本
✅ 新增代码风格与现有保持一致
✅ 有单元测试覆盖核心逻辑

【完成前请自查】
- 运行现有测试套件，确保没有回归
- 列出你修改了哪些已有文件及原因
🔄 模板 4 · 局部重构（不改行为） 谨慎操作
复制即用 · 安全重构模板 请重构 [文件/函数名]，
目标：提升可读性 / 减少重复代码 / 优化性能

黄金规则（必须遵守）：
1. 外部接口（函数签名、返回值结构）不变
2. 所有现有测试必须继续通过
3. 不引入新的依赖
4. 每次只重构一个小单元，不要大面积改动

重构完成后：
- 用 diff 形式展示改动
- 解释每处改动的理由
- 标出任何你不确定的地方（需人工确认）

# ⚠️ 如遇业务逻辑不确定，停下来问我，不要自己猜
📦 模板 5 · 依赖升级与迁移 高风险
复制即用 · 依赖迁移模板 需要将 [旧依赖@版本] 升级到 [新版本]
或迁移到 [替代库]。

请先（不要改代码）：
1. 列出 Breaking Changes（查 changelog）
2. 找出项目中所有使用该库的地方
3. 评估改动工作量（小/中/大）
4. 给出迁移建议和顺序

我确认后再执行：
- 按文件逐个迁移，每个文件一次 commit
- 每次迁移后运行相关测试
- 遇到无法自动迁移的地方标出，由我处理
⚠️ 跨大版本升级（如 React 17→18）必须人工参与决策，不能全交给 AI。

新项目搭建模板

从零开始的新项目是 Claude Code 最擅长的场景，但需要在最开始就定好规范，否则越往后越难纠偏。

新项目 从零开始
项目初始化
🎯 模板 1 · 新项目启动 PRD（产品需求文档） 第一步

在让 AI 写任何代码之前，先让它帮你把需求文档化，避免后期大返工。

核心模块搭建
🔐 模板 3 · 用户认证系统搭建 高频场景
复制即用 · 认证系统模板 搭建完整的用户认证系统，技术栈：[你的栈]

需要包含：
- 注册 / 登录 / 登出 / 刷新 Token
- JWT（access token 15min，refresh token 7天）
- 密码加密（bcrypt，salt rounds=12）

- 所有接口有请求速率限制

测试要求：
为每个认证流程写集成测试，覆盖正常和异常路径

只给出 ER 图（文字版）和字段说明。

业务描述：

请包含：

- 软删除 vs 硬删除的建议
- 需要记录操作日志的表

🌐 模板 5 · RESTful API 规范化搭建 后端通用
复制即用 · API 规范模板 搭建标准化的 RESTful API 基础架构。

要求：
- 统一响应格式：
  { code, message, data, timestamp }
- 统一错误处理中间件（捕获所有未处理异常）
- 请求参数校验（Zod / Joi）
- API 文档自动生成（Swagger/OpenAPI）
- 请求日志（记录：path、method、status、耗时）

先生成：
1. 基础路由结构示例（CRUD for User）
2. 错误码枚举定义

🎨 模板 6 · 前端组件库初始化 前端通用
复制即用 · 前端架构模板 搭建前端项目基础架构，技术栈：[React/Vue + Tailwind]

需要建立：

   - 颜色变量（primary/secondary/danger/warning）
   - 字体大小规范
   - 间距规范（4px 基准）

   Button / Input / Modal / Toast / Loading

5. 路由权限控制（需登录的路由自动重定向）

规范：组件文件结构参考 Atomic Design 原则

Bug 调试专项模板

调试是 Claude Code 最考验 Prompt 质量的场景——给的信息越精准，AI 定位越准确。掌握这些模板，告别"AI 乱猜"。

调试 排错
通用调试流程
🩺 模板 1 · 万能 Bug 报告模板 最重要

遇到任何 Bug，先用这个模板组织信息，然后给 AI，而不是直接说"我的代码出错了"。

复制即用 · Bug 报告模板 【Bug 描述】
[一句话描述问题现象]

常见坑点汇总

这些是最容易踩的坑，提前了解可以节省大量时间和挫败感。

🕳️ Top 10 最常见坑 必读
  • 幻觉式自信：AI 说"已完成"但代码有错，永远要运行一下验证
  • 依赖私自安装：AI 会悄悄 npm install 新包，要在 CLAUDE.md 里禁止
  • 过度重构：只说"优化一下"会让 AI 改很多不该改的，要明确范围
  • 测试数据污染：AI 生成的测试可能残留真实 DB 调用，检查 mock 是否正确
  • 注释欺骗：AI 会写注释说"处理了 X 情况"但代码实际上没处理
  • 环境变量泄露：AI 可能把 .env 里的值硬编码到代码里
  • API 密钥暴露：检查 AI 生成的代码是否意外把 key 写进了仓库
  • 沉默的失败：AI 的错误处理常用 console.log 而非正确上报
  • 上下文污染：长对话后 AI 开始混淆不同任务的需求
  • 无限循环修复：AI 反复改同一个 bug 却不解决根因，要换角度提问
🔒

安全与权限控制

AI 生成的代码可能存在安全漏洞，而且 Claude Code 有权限执行命令——要做好边界控制。

🛡️ 必做的安全检查 重要
  • 永不将 .env 文件允许 AI 读取或修改
  • 数据库操作：让 AI 只操作测试 DB，不连生产
  • 定期用 git grep -r "sk-" 检查是否有密钥硬编码
  • AI 生成的 SQL 要 review，防止注入风险
  • 用户输入处理代码，必须人工审查
⚠️ 在 CLAUDE.md 中明确：禁止读取 .env 文件，禁止执行 DROP/DELETE 等破坏性 SQL
🔐 限制 Claude Code 的操作权限 配置

Claude Code 可以执行 Shell 命令，但你可以通过配置限制它能做什么。

settings.json {
  "permissions": {
    "allow": ["Bash(pnpm:*)", "Bash(git:*)"],
    "deny": ["Bash(rm -rf:*)", "Bash(curl:*)"]
  }
}
